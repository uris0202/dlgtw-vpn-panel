# Сертификаты 3X-UI: только предупреждения

Текущий режим — `warning_only`. Рабочие запросы к 3X-UI используют `verify=False`:
просроченный, недоверенный или выданный для другого адреса сертификат не является
причиной их блокировки. Отдельная TLS-проба проверяет сертификат и отображает
результат в диагностике. Она не отправляет логины, пароли или HTTP-запросы.

Это осознанный компромисс: HTTPS шифрует канал, но рабочая интеграция не проверяет
подлинность сервера. Возможна подмена сервера с перехватом учётных данных.
Успех отдельной пробы не означает защиту каждого последующего рабочего запроса.
Поведение `verify=False` описано в [документации HTTPX](https://www.python-httpx.org/advanced/ssl/).

## Что будет в диагностике

- Сертификат прошёл отдельную проверку: «Успешно», с указанием режима без блокировки.
- Сертификат не прошёл проверку: «Внимание». API, клиенты, подписки и операции
  управления продолжают работать, если сам API доступен и принимает учётные данные.
- Проба не завершена из-за сети или ошибки TLS: «Не проверено». Это не меняет
  независимо полученный результат рабочего API.
- HTTP-адрес: предупреждение об отсутствии HTTPS без дополнительной блокировки.

У результата в JSON есть `policy: "warning_only"` и
`verification_enforced: false`. Ошибка сертификата не меняет настройки 3X-UI,
не выключает сервер, не отключает клиентов и не удаляет доступ.
Часовой монитор не считает такое предупреждение отказом API и не рассылает
его как недоступность VPN. Реальные сетевые ошибки и отказ авторизации остаются
ошибками API — они не могут быть исправлены отключением проверки сертификата.

Ограничение переадресаций рабочих запросов на другой origin (схема, хост, порт)
сохранено. Оно независимо от результата проверки сертификата.

## Установка

Используйте новый архив вместо предыдущего `xui-tls-verification-20261101.zip`.
Этот пакет подходит и если строгий режим уже установлен, и если ещё не установлен.

Загрузите `xui-tls-warning-mode-20261101.zip` в `/root/` рабочего сервера сайта:

```sh
cd ~/vpnpanel &&
mkdir -p ~/vpnpanel-backups &&
umask 077 &&
tar --exclude='./.git' --exclude='./frontend/node_modules' \
    --exclude='./frontend/.next' --exclude='./backups' \
    --exclude='./relay/control/*.sock' \
    -czf ~/vpnpanel-backups/pre-xui-tls-warning-$(date +%Y%m%d-%H%M%S).tar.gz . &&
unzip -o ~/xui-tls-warning-mode-20261101.zip -d ~/vpnpanel &&
sh scripts/install-xui-tls-verification.sh
```

Имя установщика сохранено для совместимости, но его содержимое обновлено:
он применяет только режим предупреждений. Архив содержит полные готовые файлы.

Сначала сохраняются файлы проекта и `.env`, затем установщик дополнительно
сохраняет PostgreSQL dump и проверяет его оглавление. Не публикуйте эти резервные
копии: они могут содержать секреты. Проверка оглавления не является тестовым
восстановлением базы.

Новый образ проходит тесты и проверку доступа к API. Предупреждение сертификата
не останавливает установку. Реальная ошибка доступа к API останавливает замену
контейнеров до её начала, чтобы не ухудшить работающую панель.

Обновляется backend, перезапускается Caddy. Если монитор установлен, его образ
тоже пересобирается; работающий монитор пересоздаётся с сохранением истории
инцидентов, остановленный остаётся остановленным. Миграций базы нет.
Frontend, HAProxy, зарубежные Xray, UUID, REALITY и VPN-маршруты не меняются.
Доступ к панели во время пересоздания контейнеров может кратковременно прерваться.

## После установки

Проверка в терминале выводит `status: "reachable"` для рабочего API, даже если
внутри поля `certificate` находится `state: "warning"`. Эти результаты независимы.

Итоговый отчёт:

```text
/root/vpnpanel-backups/xui-tls-warning-ДАТА-ВРЕМЯ/diagnostics.jsonl
```

Откройте **Серверы → Диагностика** и выполните новую проверку.
При плохом сертификате строка **Защита канала управления** покажет предупреждение
и прямо сообщит, что рабочие запросы не блокируются.
