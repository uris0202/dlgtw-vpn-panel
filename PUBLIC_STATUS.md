# Публичная страница состояния

Страница `https://dlgtw.ru/status` доступна без входа. Ссылка «Статус» добавлена
в общую шапку покупки, ЛК и новостей. На странице есть текущие направления,
результаты инфраструктурных проверок, время проверки, открытые проблемы
и последние опубликованные новости из существующего блока.

## Что именно проверено

Источник — действующий ежечасный монитор на сервере в Петербурге.
Он по-прежнему подтверждает обнаруженную ошибку повторной проверкой через
настроенный интервал и уведомляет в Telegram. Страница не меняет частоту
проверок, настройки REALITY, клиентов, тарифы и сроки доступа.

Показаны отдельные уровни:

- TCP-маршрут: VPN-порты, вход каскада, конфигурация маршрута и статус назначения HAProxy.
- Процесс на узле: состояние Xray по данным канала управления.
- Канал управления: доступность API, без публикации его адреса и ошибок входа.
- Сбор диагностики: удалось ли получить результаты.

Успешный TCP-порт сам по себе не называется успешным VPN-сеансом.
Ошибка API при доступном TCP-маршруте показывается как неполная проверка,
а не доказанный отказ VPN. Доступность из сети клиента/его оператора не измеряется.
Новая страница не является защитой от блокировок и не добавляет резервный вход.

Публичная выдача содержит только текущие включённые направления панели,
их уже используемые публичные названия/страны и обезличенные результаты.
Названия направлений доступны и на странице покупки: не записывайте в них секреты.
Служебные IP/URL/порты, UUID, ключи, клиентские имена, Telegram и тексты
диагностических ошибок не публикуются. Сбои одного типа объединяются.
Отключение/удаление сервера не объявляется подтверждённым восстановлением.

## Как устроено

После завершённого цикла монитор атомарно пишет `public-status.json` в
существующий volume `vpn_monitor_data`. В нём только разрешённые поля.
Backend получает этот же volume только для чтения. Файл инцидентов не отдаётся
по HTTP. Новый GET `/api/public/status` повторно отбирает разрешённые поля,
возвращает `Cache-Control: no-store` и ограничивает частоту запросов.
Посетитель не запускает диагностику и не создаёт дополнительных запросов к 3X-UI.

Без снимка, при повреждённом/слишком большом файле, будущем времени, ошибке
цикла или heartbeat старше пяти минут состояние неизвестно. Снимок также
устаревает через интервал монитора плюс 15 минут (по умолчанию 75 минут).
Страница обновляет выдачу раз в минуту на видимой вкладке и при возвращении
на неё. При ошибке HTTP старые зелёные результаты не выдаются за актуальные.

Монитор и публичная страница находятся на одном VDS. Если сам сервер сайта
недоступен, страница тоже может не открыться. Внешний мониторинг из другой сети
и полноценный VPN-сеанс остаются отдельным следующим этапом.

## Установка

Загрузите `public-status-20261103.zip` в `/root/` рабочего сервера сайта.
Сначала сохраните проект до распаковки:

```sh
cd ~/vpnpanel &&
mkdir -p ~/vpnpanel-backups &&
umask 077 &&
tar --exclude='./.git' --exclude='./frontend/node_modules' \
    --exclude='./frontend/.next' --exclude='./backups' --exclude='*.sock' \
    -czf ~/vpnpanel-backups/pre-public-status-$(date +%Y%m%d-%H%M%S).tar.gz . &&
unzip -o ~/public-status-20261103.zip -d ~/vpnpanel &&
sh scripts/install-public-status.sh
```

Установщик требует уже работающий `vpn-monitor`. Сохраняются PostgreSQL dump
и файл текущих инцидентов в `~/vpnpanel-backups/public-status-ДАТА-ВРЕМЯ/`.
Проверяется читаемость оглавления дампа, не пробное восстановление.
Копия проекта включает `.env`, поэтому архивы приватные, не для GitHub.

До пересоздания собираются backend/frontend/monitor, выполняются оба набора
тестов и проверяется конфигурация монитора. Затем пересоздаются эти три
контейнера с сохранением существующего volume и перезапускается Caddy.
Небольшая недоступность сайта и перерыв мониторинга ожидаемы.
Сохранённые инциденты не очищаются и не должны рассылаться повторно.
HAProxy и зарубежные Xray не перезапускаются, firewall и маршруты не меняются.
Миграций, новых зависимостей и обязательных изменений `.env` нет.
В конце установщик обращается к новому API из backend-контейнера и требует
`public_status_fresh: true`: это проверяет чтение снимка из общего volume,
но не требует «зелёных» результатов всех VPN-направлений.

После установки:

```sh
docker compose ps backend frontend vpn-monitor
docker compose logs --tail=35 vpn-monitor
curl -fsS https://dlgtw.ru/api/public/status
```

Откройте `/status` в приватном окне без авторизации. После первого законченного
цикла монитора появятся результаты. Если пока написано «Нет актуальных данных»,
не меняйте VPN-порты или ключи: сначала проверьте журнал монитора.

права общего volume и работу настоящего монитора проверяет установка на сервере.
