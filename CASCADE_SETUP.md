# DLGTW: каскад через Петербург и единая подписка

Схема: приложение клиента -> 139.100.235.247:отдельный_порт -> выбранный VPN-сервер -> интернет.
Германия, Амстердам и Польша остаются выходными серверами. Петербург передаёт зашифрованное TCP-соединение; авторизация, срок и лимиты остаются в существующем 3X-UI. HTTPS сайта dlgtw.ru продолжает работать на 443 через Caddy.

## Что подготовлено

- Один HAProxy TCP listener на каждый активный VLESS inbound. Порты выделяются начиная с 24443; фактический список выводится при установке. Повторный запуск сохраняет ранее выделенные порты.
- Адреса и VPN-порты автоматически читаются из существующей базы и 3X-UI. Пароли, UUID и приватные ключи в конфигурацию HAProxy и отчёт не попадают.
- Перед включением проверяется TCP-доступность каждого VPN-порта из Петербурга. Доступность веб-панели сама по себе ещё не подтверждает доступность VPN-порта.
- Единая персональная подписка в личном кабинете. В ней только серверы из оплаченных и успешно выданных заказов или административного доступа. Неоплаченные и отменённые заказы не добавляют серверы.
- Выключенные, истёкшие и исчерпавшие лимит клиенты исключаются из выдачи. Проверка остаётся и на самих VPN-серверах.
- Отдельный токен подписки не открывает личный кабинет. Сброс доступа к кабинету меняет ссылку подписки.
- Если один из оплаченных серверов временно не отвечает, обновление подписки возвращает 503, а не неполный список.

## Установка

Работать по SSH на сервере сайта 139.100.235.247. Сначала загрузить ZIP в /root, затем:

```sh
cd ~/vpnpanel
mkdir -p ~/vpnpanel-backups
STAMP=$(date +%Y%m%d-%H%M%S)
tar --exclude='./frontend/node_modules' --exclude='./frontend/.next' --exclude='./backups' --exclude='./.git' -czf ~/vpnpanel-backups/pre-cascade-files-$STAMP.tar.gz .
```

Архив файлов включает текущий .env; хранить его приватно. Затем распаковать полученный ZIP поверх проекта и запустить:

```sh
sh scripts/setup-vpn-relay.sh 139.100.235.247
```

Скрипт сначала сохраняет резервную копию PostgreSQL в ~/vpnpanel-backups/cascade-ДАТА/database.sql. Затем собирает существующие backend/frontend, запускает тесты, проверяет 3X-UI и VPN-порты, проверяет конфигурацию HAProxy и запускает переадресацию. После этого включает новые адреса подписки и ждёт готовности backend/frontend. Миграции БД не нужны. При ошибке после начала запуска возвращает предыдущую конфигурацию промежуточного сервера.

Готовность HTTPS проверяется с повторными попытками, в том числе после отказа в соединении и ответов 502/503 во время запуска. Проверка идёт через 127.0.0.1 с настоящим именем dlgtw.ru и проверкой сертификата, чтобы исключить зависимость от публичного DNS и маршрута к собственному внешнему IP. Доступность из сети клиента затем нужно проверить отдельно.

Если предыдущая установка дошла до готовности backend/frontend и остановилась на проверке HTTPS, продолжить сохранённую настройку без пересборки можно так:

```sh
cd ~/vpnpanel
sh scripts/setup-vpn-relay.sh --resume
```

Режим продолжения использует сохранённые routes.failed.json или routes.next.json и подготовленный haproxy.next.cfg. Он также делает резервную копию базы, проверяет конфигурацию HAProxy, включает промежуточный сервер и ждёт готовности сайта. Если подготовленных файлов нет, скрипт остановится с инструкцией выполнить полную установку.

Если UFW уже активен, скрипт добавляет разрешения только для выделенных TCP-портов. Внешний firewall в панели хостинга нужно настроить отдельно: разрешить входящий TCP для портов, напечатанных скриптом. UDP-порты и веб-порты управления 3X-UI открывать не требуется.

Если подготовка остановилась на конкретном Server #ID, исходящие соединения к его панели или VPN-порту недоступны из Петербурга. Новая схема не включается. Проверьте firewall и реальную доступность этого адреса из сервера сайта.

Новые серверы/inbound или смена VPN-порта требуют повторного запуска скрипта. Изменение IP адреса сервера также требует повторной генерации: HAProxy получает проверенный IP, а не произвольную строку из базы.

## Проверка

```sh
cd ~/vpnpanel
docker compose --profile relay ps
docker compose --profile relay logs --tail=60 vpn-relay
curl -fsS https://dlgtw.ru/api/health
cat relay/ports.next.txt
```

Открыть личный кабинет клиента на https://dlgtw.ru/account, скопировать «Единая подписка DLGTW VPN» и добавить её в VPN-приложение вместо старых трёх подписок. При изменении оплаченных серверов URL остаётся прежним, список обновляется после обновления подписки в приложении. Если тариф разрешает два выбранных сервера, появятся эти два, а не все три.

Администратор может скопировать тот же URL кнопкой «Подписка» в разделе «Кабинеты клиентов» и отправить его клиенту.

В каждом VLESS-профиле адресом подключения должен быть 139.100.235.247, а портом — один из выданных промежуточных портов. UUID, Reality public key, SNI, short ID и flow должны сохраниться. Проверить подключение из обычного домашнего/мобильного интернета отдельно к каждой стране и проверить внешний IP. Только эта проверка подтверждает работу VPN из сети клиента: локальные тесты и открытый TCP-порт не проверяют весь VLESS/Reality сеанс.

Если приложение уже импортировало старые прямые конфигурации, одна лишь перезагрузка сайта их не изменит. Нужна новая общая подписка.

## Доступ по SSH через Петербург

Для аварийного доступа можно использовать существующий SSH-сервер сайта как jump host:

```sh
ssh -J root@139.100.235.247 root@IP_VPN_СЕРВЕРА
```

Заменить IP_VPN_СЕРВЕРА реальным адресом Германии или Амстердама. Должны быть доступны SSH-порт VPN-сервера из Петербурга и разрешён SSH forwarding на сервере сайта. Учетные данные нужны для обоих серверов.

## Откат

Сначала отключить переписывание адресов, сохранив конфигурацию, затем остановить промежуточный сервер:

```sh
cd ~/vpnpanel
mv relay/routes.json relay/routes.disabled.json
docker compose --profile relay stop vpn-relay
```

Общая подписка начнёт выдавать прежние прямые адреса. Чтобы вернуться к каскаду, запустить скрипт установки ещё раз. Исходные файлы панели можно восстановить из pre-cascade-files-ДАТА.tar.gz и пересобрать backend/frontend. Восстановление PostgreSQL для отката этого обновления не требуется: схема БД не меняется.

## Условия

Это TCP-переадресация для существующих VLESS TCP/Reality/TLS и совместимых TCP-транспортов. KCP/QUIC через этот промежуточный сервер не поддерживаются. Скрипт остановится при обнаружении такого активного VLESS inbound.

Весь VPN-трафик и нагрузка на соединения проходят через сервер сайта. Его пропускная способность и лимит трафика ограничивают всех клиентов. Эта схема помогает, когда из сети клиента заблокирован адрес выхода, но из Петербурга VPN-порт доступен. Если провайдер блокирует сам протокол, выбранные порты или адрес Петербурга, результат может отличаться; после установки обязательна проверка из сети клиента.

На выходных серверах источником соединений будет IP Петербурга. Если используется ограничение устройств по исходным IP, через такую TCP-переадресацию оно не различает устройства клиентов.

Техническая основа: [HAProxy TCP mode](https://docs.haproxy.org/3.0/configuration.html), [Xray REALITY](https://xtls.github.io/config/transports/reality).
Локальная проверка HTTPS использует [curl --resolve](https://curl.se/docs/manpage.html#--resolve).
