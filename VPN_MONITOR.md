# Ежечасный мониторинг VPN с уведомлениями в Telegram

Монитор работает отдельным контейнером `vpnpanel-vpn-monitor` на рабочем VDS
сайта. Компьютер администратора и открытый браузер для него не нужны.
Новые API, миграции базы и изменения интерфейса не добавляются.

## Что и когда проверяется

- Первый цикл запускается сразу после старта контейнера, следующие — раз в час.
- Проверяются все серверы, включённые в панели: Germany, Amsterdam, Poland
  и новые включённые серверы, которые будут добавлены позже.
- Раздельно проверяются API 3X-UI, состояние Xray по данным 3X-UI, VPN-порты
  зарубежных серверов и публичные входные порты каскада.
- Для каскада дополнительно проверяются соответствие маршрутов и статус
  `destination` через read-only команду HAProxy `show stat`. Принимающий
  соединения входной порт сам по себе не считается подтверждением доступности
  следующего узла.
- Если есть ошибка, через 60 секунд повторно проверяется затронутый сервер.
  Только повторившаяся ошибка открывает инцидент.
- В настроенный Telegram-чат отправляется сообщение с названием сервера
  и конкретным проблемным слоем. Недоступность API не называется отказом VPN.
- При исправном состоянии сообщений нет. Неизменившийся сбой не рассылается
  каждый час. После подтверждённого успешного результата приходит восстановление.
  Проверка восстановления выполняется в следующем часовом цикле, не каждую минуту.
- Если Telegram временно не принимает сообщения, отправка повторяется раз в
  пять минут через существующий Telegram-сервис с его сетевыми повторами.
- Используются текущие токен бота, Chat ID и переключатель Telegram-уведомлений
  из настроек панели. Изменения настроек считываются без перезапуска монитора.
- Намеренно выключенные или удалённые серверы больше не опрашиваются.
  Их отключение администратором не объявляется восстановлением связи.

При нескольких проблемах одного сервера сообщения группируются. Появление новой
проблемы в другом слое может вызвать дополнительное сообщение.
Состояние инцидентов сохраняется в отдельном Docker volume `vpn_monitor_data`;
обычное пересоздание контейнера не сбрасывает защиту от повторов.
Секреты Telegram, UUID и ключи клиентов в этот volume и сообщения не записываются.
Имя сервера в уведомление попадает: не используйте в нём секретные данные.

## Установка

Сначала в **Настройки → Telegram** убедитесь, что уведомления включены,
токен и Chat ID сохранены, а существующая кнопка тестового сообщения работает.
При отсутствии настроек Telegram установщик не запустит монитор.

Загрузите `vpn-hourly-monitor-20261101.zip` в `/root/` рабочего сервера сайта.
Не устанавливайте его на отключённую тестовую облачную машину.
На сервере сайта выполните:

```sh
cd ~/vpnpanel &&
mkdir -p ~/vpnpanel-backups &&
umask 077 &&
tar --exclude='./.git' --exclude='./frontend/node_modules' \
    --exclude='./frontend/.next' --exclude='./backups' \
    --exclude='./relay/control/*.sock' \
    -czf ~/vpnpanel-backups/pre-vpn-monitor-$(date +%Y%m%d-%H%M%S).tar.gz . &&
unzip -o ~/vpn-hourly-monitor-20261101.zip -d ~/vpnpanel &&
sh scripts/install-vpn-monitor.sh
```

До распаковки сохраняется копия файлов проекта, включая `.env`. Не публикуйте
её: внутри могут быть секреты. Установщик дополнительно создаст `pg_dump -Fc`
в `/root/vpnpanel-backups/vpn-monitor-ДАТА-ВРЕМЯ/` и проверит его оглавление
через `pg_restore --list`. Это не пробное восстановление базы.

Затем собирается образ только нового монитора, выполняются backend-тесты,
проверяется наличие настроек Telegram и включённых серверов. Только после этого
запускается `vpn-monitor`. Некоторые тесты корневых shell-скриптов и тестовой
облачной машины внутри образа будут `skipped`: для них нужно полное дерево
репозитория. Локально эти тесты выполнены.

Работающие backend, frontend, Caddy, HAProxy и зарубежные Xray установщик
не пересоздаёт и не перезапускает. UUID, REALITY и firewall не меняются.
Файл `backend/Dockerfile` получает только каталог хранения состояния монитора;
это не требует сейчас пересобирать работающий backend.

## Проверка запуска

```sh
cd ~/vpnpanel
docker compose ps vpn-monitor
docker compose logs --tail=60 vpn-monitor
```

Ожидаемый статус — `Up ... (healthy)`. Это исправность самого монитора,
а не утверждение о доступности всех VPN-серверов. Первый цикл может занять несколько минут,
особенно если нужна повторная проверка ошибки. В журнале будут:

```text
VPN monitor started: interval=3600s confirmation=60s
Monitor cycle completed: servers=3 checks={'up': ..., 'down': 0, 'unknown': ...}
```

`unknown` означает неподдерживаемую/неполную проверку, а не автоматически
исправный сервер. Например, 1 успешная TCP-попытка из 2 не закрывает ранее
открытый инцидент и сама по себе не создаёт уведомление о полной недоступности.
Ошибки чтения диагностики или HAProxy отмечаются как невозможность проверить
соответствующий слой, без утверждения об отказе самого VPN.

Если всё исправно, сообщение о запуске или «всё хорошо» в Telegram не приходит.
Не отключайте VPN клиентам ради теста: доставку проверяйте штатной кнопкой
тестового сообщения в настройках Telegram.

`unhealthy` требует проверки журнала: причины включают ошибки циклов, устаревший
heartbeat, отсутствие настроек Telegram и неотправленные уведомления.
Рабочий цикл пытается повторить временные ошибки через пять минут.
Docker автоматически перезапустит завершившийся процесс согласно
`restart: unless-stopped`, но сам по себе статус `unhealthy` не является командой
перезапуска контейнера.

## Ограничения

1. Это мониторинг API, процесса, маршрутов и TCP. Он не выполняет VLESS/REALITY-
   рукопожатие, не измеряет скорость и не доказывает работу интернета через VPN.
2. Проверка идёт из сети рабочего VDS/контейнера и по данным HAProxy.
   Блокировку только у конкретного мобильного оператора она может не заметить.
3. Часовой интервал означает, что обнаружение может занять около часа плюс
   минуту подтверждения и время сетевых запросов. Короткий сбой между циклами
   может остаться незамеченным.
4. Если полностью отключится сам VDS, его сеть, PostgreSQL или доступ к Telegram,
   отправку нельзя гарантировать. Для контроля всей точки входа нужен независимый
   внешний монитор с другой площадки. Этот пакет его не создаёт.
5. Предупреждения статического аудита REALITY, отсутствие Vision и предупреждения
   отдельной проверки сертификатов не считаются недоступностью. В режиме
   `warning_only` плохой сертификат сам по себе не блокирует API и не вызывает
   сообщение о его отказе. Реальные сетевые ошибки или отказ авторизации
   продолжают отслеживаться отдельно.
6. После неоднозначного сетевого тайм-аута Telegram мог принять сообщение,
   но не вернуть подтверждение. В таком случае при повторе возможен дубликат;
   абсолютная доставка «ровно один раз» не гарантируется.
7. Как и ручная диагностика, аудит ограничен первыми 12 VLESS inbounds и
   12 сохранёнными маршрутами одного сервера.
8. Повреждённое хранилище инцидентов не сбрасывается автоматически. Монитор
   покажет ошибку в журнале; не удаляйте volume без разбора причины. Потеря
   volume сбросит историю оповещений, но не VPN-клиентов и не основную базу.

HAProxy-статистика читается по [официальному Runtime API](https://www.haproxy.com/documentation/haproxy-runtime-api/reference/show-stat/).
Для сохранения инцидентов используется [постоянный Docker volume](https://docs.docker.com/engine/storage/volumes/).

## Остановка и запуск

Только монитор, без влияния на VPN:

```sh
cd ~/vpnpanel
docker compose stop vpn-monitor
```

Возобновить:

```sh
cd ~/vpnpanel
docker compose up -d vpn-monitor
```

Не выполняйте `docker compose down -v`: это удаляет не только состояние монитора,
но и другие Docker volumes проекта, включая PostgreSQL.

## Интервал

По умолчанию час, менять `.env` для запуска не нужно. Значения можно явно задать
в существующем `.env` (не добавлять повторные строки с теми же именами):

```dotenv
VPN_MONITOR_INTERVAL_SECONDS=3600
VPN_MONITOR_CONFIRM_SECONDS=60
```

После изменения примените только монитор:

```sh
cd ~/vpnpanel
docker compose up -d --no-deps --force-recreate vpn-monitor
```
