# Проверочный HTTPS-запрос через VPN

## Назначение

Действующий ежечасный монитор получает дополнительную необязательную проверку:
временный Xray-клиент подключается по VLESS через тот же публикуемый адрес
и порт, что клиентская подписка, и запрашивает HTTPS-страницу через VPN-выход.
REALITY/TLS и параметры берутся из существующего экспорта профиля.

Проверка идёт с VDS панели в Петербурге. Она не измеряет доступность из мобильной
или домашней сети клиента, не гарантирует обход ТСПУ, не измеряет скорость,
UDP и доступность всех сайтов. Её сбой не доказывает отказ всех VPN-приложений:
возможна несовместимость проверочного клиента с конкретной конфигурацией.
Ничего автоматически не переключается, не блокируется и не продлевается.

## Изоляция

- Проверка выключена до отдельной команды настройки.
- Используется только служебный клиент `dlgtw-monitor` с группой `DLGTW Monitor`
  и комментарием `DLGTW health probe (service profile)`.
- Обычный клиент с совпавшим именем, в том числе другого регистра, не используется
  и не переписывается. Первичная настройка проверяет все включённые серверы до
  первого создания. При частичной ошибке уже созданные служебные профили остаются,
  чужие профили не удаляются; повторный запуск распознаёт свои записи.
- Профиль создаётся бессрочным, без лимита трафика/IP, без ЛК и заказа.
  UUID и subId новые; существующие клиенты, тарифы, сроки и ключи не меняются.
  Служебный профиль появится в административной таблице и статистике как отдельный
  клиент. Это небольшой дополнительный служебный трафик, не проверка скорости.
- Если служебный профиль выключен или получил ограничения, проверка становится
  неизвестной. Монитор не включает, не продлевает и не сбрасывает его автоматически.

Используется официальный Xray 26.10.31, образ закреплён по digest
`sha256:ceabeac03a89d991d2a247361825c1d1d2e9c91cd5dc010f298c7dc0c2f325c9`.
Он добавлен только в отдельную цель сборки монитора, не в backend API.
Источники: [официальный проект](https://github.com/XTLS/Xray-core),
[Dockerfile выпуска](https://github.com/XTLS/Xray-core/blob/v26.10.31/.github/docker/Dockerfile).

Xray запускается непривилегированным короткоживущим процессом. Его HTTP-прокси
слушает только 127.0.0.1 внутри контейнера, никаких новых публичных портов нет.
Конфигурация с UUID/ключом находится во временной приватной папке, файл 0600;
после проверки процесс завершается, файл удаляется. В аргументах процесса только
путь к файлу. Логи Xray выключены. Ему не передаются переменные PostgreSQL/Telegram.
У проверочного клиента единственный outbound VLESS, прямого fallback нет.

Поддерживаются существующие VLESS TCP/raw с REALITY или TLS. Другие транспорты
пока дают «Нет данных», а не ложную доступность. Для TLS проверка сертификата
включена. Это не меняет принятую политику предупреждений сертификата API 3X-UI.

## Как определяется результат

Запрашиваются `https://www.gstatic.com/generate_204` и, при неудаче,
`https://cp.cloudflare.com/generate_204`. Редиректы не принимаются, сертификат
HTTPS проверяется; достаточно успешного HTTP 204 через VPN. При ошибочном HTTP
большой ответ не скачивается. Внешние сервисы видят служебный запрос с IP выхода;
данные клиентов им не отправляются.

Если оба VPN-запроса не прошли, выполняется отдельная прямая контрольная проверка.
Она никогда не считается успешным VPN. Если контроль работает, фиксируется сбой
проверочного VPN-запроса; если контроль тоже не работает, результат неизвестен.
Ошибки конфигурации/запуска движка также неизвестны, а не объявляются отказом VPN.

Существующее подтверждение ошибки повторным циклом и уведомления Telegram
сохраняются. Новый слой отделён от TCP/API. При намеренном выключении полной
проверки её инциденты снимаются без ложного сообщения о восстановлении;
остальные инциденты не затрагиваются. Состояние публикуется на `/status`
без UUID, адресов, ключей и имени служебного клиента.

## 1. Установить возможность проверки

Загрузите `vpn-session-monitor-20261103.zip` в `/root/` рабочего сервера сайта:

```sh
cd ~/vpnpanel &&
mkdir -p ~/vpnpanel-backups &&
umask 077 &&
tar --exclude='./.git' --exclude='./frontend/node_modules' \
    --exclude='./frontend/.next' --exclude='./backups' --exclude='*.sock' \
    -czf ~/vpnpanel-backups/pre-vpn-session-$(date +%Y%m%d-%H%M%S).tar.gz . &&
unzip -o ~/vpn-session-monitor-20261103.zip -d ~/vpnpanel &&
sh scripts/install-vpn-session-monitor.sh
```

Сохраняются проект с `.env`, PostgreSQL dump и состояние монитора; архивы приватные.
Проверка dump — чтение оглавления, не пробное восстановление.
Нужен доступ сервера к официальному ghcr.io для получения закреплённого образа.
До замены контейнеров выполняются обычные тесты и отдельные тесты с настоящим
Xray внутри образа монитора. Если сборка/проверка не прошла, пересоздания нет.

Перезапускаются backend/frontend/Caddy и монитор с прежним volume. HAProxy,
порты, DNS, REALITY и зарубежные Xray не меняются и не перезапускаются.
Инсталлятор не создаёт служебных профилей и не включает проверку автоматически.
Существующая настройка при повторной установке сохраняется.

## 2. Явно создать служебные профили и включить

Сначала можно выполнить только предварительный просмотр без создания:

```sh
cd ~/vpnpanel
docker compose exec -T vpn-monitor python -m app.scripts.configure_vpn_canary
```

Для включения на всех включённых серверах панели:

```sh
docker compose exec -T vpn-monitor python -m app.scripts.configure_vpn_canary --create-profile --enable &&
docker compose restart vpn-monitor
```

Это отдельное разрешённое действие создаёт только новые служебные профили.
Номер подходящего inbound определяется на каждом сервере отдельно, не считается
равным 1 везде. При первичном создании выбирается первый включённый поддерживаемый
inbound; это не проверка всех возможных inbound/транспортов на многопротокольном
сервере. Обычные платные клиенты не перезаписываются. Наличие собственных
профилей и конфигурация проверяются до включения; фактический HTTPS-запрос
выполнит первый цикл монитора после перезапуска. Настройка хранится в приватном
`canary.json` существующего volume и не требует правки `.env`.

Не запускайте команду параллельно в двух SSH-сессиях. Создание профилей на разных
серверах не является одной транзакцией. Если операция прервалась, сначала проверьте
группу `DLGTW Monitor`; не удаляйте обычных клиентов и не меняйте их UUID.

## 3. Проверить

```sh
docker compose exec -T vpn-monitor python -m app.scripts.configure_vpn_canary --show
docker compose ps vpn-monitor
docker compose logs --tail=50 vpn-monitor
curl -fsS https://dlgtw.ru/api/public/status
```

После цикла монитора на `/status` появится строка «Запрос через VPN»:
«HTTPS через VPN прошёл», «Запрос не прошёл» или «Нет данных».
До настройки — «Не настроена». Не публикуйте VLESS-ссылки/дампы/`.env`.
Неизвестный результат требует проверки профиля/маршрута/совместимости, а не
слепой замены ключей. Отдельная контрольная точка в сети клиента остаётся
следующим этапом, пока результаты относятся только к Петербургу.

## Выключение без изменения рабочих подключений

```sh
docker compose exec -T vpn-monitor python -m app.scripts.configure_vpn_canary --disable &&
docker compose restart vpn-monitor
```

Служебные профили остаются, их можно удалить позже вручную через существующий
раздел клиентов. Не удаляйте их во время активной проверки.

Новых API, миграций и npm/pip-зависимостей нет. Локальный стенд использует
официальный Xray с проверенной SHA256, два настоящих процесса REALITY/VLESS/Vision
и приватный HTTPS-сервер. Проверяется успешная передача, неверный UUID и
недоверенный сертификат; стенд не обращается к рабочим серверам клиентов.
Docker локально недоступен; Linux-сборку и интеграционные проверки выполняет
установщик до пересоздания контейнеров.
