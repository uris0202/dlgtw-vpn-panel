# Диагностика VPN-серверов без изменения настроек

Рабочий VDS остаётся точкой входа. Этот пакет не переносит панель на облачный
сервер, не меняет DNS, REALITY, UUID клиентов, порты, firewall или маршруты.
Защиту от блокировок он не гарантирует: сначала нужны измерения существующей схемы.

## Установка

Архив `vpn-server-diagnostics-20261031.zip` содержит полные готовые файлы,
а не diff. Загрузите его в `/root/` рабочего сервера с сайтом.
Не выполняйте установку на отключённой тестовой облачной машине.

Выполните на сервере сайта одним блоком:

```sh
cd ~/vpnpanel &&
mkdir -p ~/vpnpanel-backups &&
umask 077 &&
tar --exclude='./.git' --exclude='./node_modules' --exclude='./frontend/node_modules' \
    --exclude='./frontend/.next' --exclude='./backups' \
    -czf ~/vpnpanel-backups/pre-server-diagnostics-$(date +%Y%m%d-%H%M%S).tar.gz . &&
unzip -o ~/vpn-server-diagnostics-20261031.zip -d ~/vpnpanel &&
sh scripts/install-server-diagnostics.sh
```

До распаковки сохраняется копия исходников и `.env`. Она может содержать секреты:
не публикуйте её. Установщик дополнительно сохраняет `pg_dump -Fc` и проверяет,
что `pg_restore --list` читает оглавление. Это не пробное восстановление базы.
Автоматические существующие резервные копии базы продолжают работать отдельно.

Затем собираются backend/frontend, запускаются их тесты и пересоздаются только
backend/frontend. Caddy перезапускается для обновления адресов контейнеров.
Во время пересоздания панель кратковременно недоступна. Работающий HAProxy
и зарубежные Xray не перезапускаются. Миграций базы в этом обновлении нет.
Если резервная копия, сборка или тесты завершатся ошибкой, замена контейнеров
не начнётся. Не продолжайте вручную после ошибки: пришлите её вывод.

В Docker некоторые тесты shell-установщиков могут выводиться как `skipped`:
в образ backend не копируется корневая папка `scripts/`. Это не пропуск проверок
самой диагностики. Тесты установщиков выполняются локально и в GitHub Actions
с полным деревом репозитория.

В конце выполняется аудит всех настроенных серверов. Отчёт и резервная копия
базы находятся в напечатанной папке:

```text
/root/vpnpanel-backups/server-diagnostics-ДАТА-ВРЕМЯ/
    database.dump
    database.list
    diagnostics.jsonl
```

Отчёт с результатами выводится в терминал. Состояние `error` внутри отчёта означает
неудачную проверку соответствующего слоя, а не ошибку установки. Выключенные
в панели серверы не опрашиваются. При полном сбое команды аудита панель уже может
быть обновлена: не восстанавливайте базу автоматически, сначала проверьте вывод.

## В панели

Откройте **Серверы → Диагностика**. Проверки выполняются вручную, только после
нажатия. На сервер доступно до трёх запросов в минуту на администратора;
в одном процессе backend одновременно выполняются не более двух проверок.
Закрытие окна прекращает ожидание в браузере, но начатая проверка backend может
ещё завершаться. При `429` подождите минуту перед повтором.

Отдельно показаны:

- HTTPS страницы покупки и публичный `/api/health` панели.
- Авторизация 3X-UI и получение inbounds. Обычный вход создаёт сессию 3X-UI,
  но конфигурация VPN не изменяется.
- Состояние и версия Xray, если версия 3X-UI отдаёт GET `/panel/api/server/status`.
  Неподдерживаемый ответ означает «Не проверено», а не «Xray остановлен».
- Соответствие сохранённого маршрута работающему HAProxy и текущему порту inbound.
- Две TCP-пробы к каждому включённому VLESS inbound зарубежного сервера.
  Если API не ответил, порт берётся из сохранённого маршрута, когда он доступен.
- Две TCP-пробы публичных входных портов каскада.
- Статический аудит REALITY: формат и согласованность ключей, serverNames/SNI,
  shortIds, формат target/dest, flow Vision и сохранённый fingerprint.

Новые результаты диагностики на карточке сохраняются до обновления страницы
или повторной загрузки списка. Старый статус статистики 3X-UI показан отдельно:
он не является результатом проверки VPN и может быть закэширован.

Кнопка **Отчёт** скачивает JSON. В него не включаются пароли, ключи, UUID,
email клиентов, токены подписок, полный адрес панели 3X-UI и её конфигурация.
Имя и ID сервера, номера портов, время и результаты остаются в отчёте.
Не помещайте секреты в название сервера; перед пересылкой просмотрите отчёт.

## Границы проверки

- Проверка идёт из контейнера backend. Сеть host HAProxy, сеть пользователя
  и мобильный оператор проверкой не покрыты. Ограничения hairpin/NAT могут
  мешать контейнеру обратиться к публичному адресу собственного сервера.
- Открытый TCP-порт не доказывает успешное VLESS/REALITY-рукопожатие или работу
  интернета через VPN. Рукопожатие и клиентская подписка всегда отмечены
  «Не проверено»: клиентские UUID и токены этот аудит не запрашивает.
- Две попытки — краткая проба, не доказательство долговременной стабильности,
  пропускной способности или наличия/отсутствия блокировки.
- Формат target/dest проверяется локально. Его TLS, версия TLS и доступность
  непосредственно с зарубежного VPN-сервера не проверяются.
- Формат fingerprint в сохранённых данных 3X-UI может отличаться от фактической
  настройки v2rayTun. Отсутствие flow Vision — предупреждение, не приговор.
- Аудит ограничен первыми 12 VLESS inbounds и 12 сохранёнными маршрутами
  одного сервера. У TCP/HTTP есть тайм-ауты; системное разрешение DNS может
  дополнительно увеличить ожидание.
- Режим сертификатов — `warning_only`. Рабочая интеграция использует
  `verify=False`; отдельное TLS-подключение без HTTP-запросов и учётных данных
  проверяет срок, доверие и соответствие адресу. Ошибка даёт «Внимание» в строке
  канала управления, но не блокирует рабочие запросы к 3X-UI. Зелёный результат
  означает только успех отдельной пробы, а не защиту каждого API-запроса от подмены.

Состояние «Успешно» относится только к конкретной строке. Оно не означает
защищённость от обнаружения или блокировки. Xray обновлять/перезапускать,
SNI и ключи менять без анализа отчёта не нужно.

## Повторный аудит из терминала

Все включённые серверы, без клиентских токенов и без изменений конфигурации:

```sh
cd ~/vpnpanel &&
docker compose exec -T backend python -m app.scripts.audit_vpn_readiness --all
```

Только сервер с ID 2:

```sh
cd ~/vpnpanel &&
docker compose exec -T backend python -m app.scripts.audit_vpn_readiness --server-id 2
```

Это команды после установки. Для выводов о текущих production-настройках нужен
их фактический результат: локальные тесты проверяют код, а не ваши живые узлы.

## Что делать после отчёта

1. Исправлять конкретный слой: API, маршрут, TCP или настройки REALITY.
   Не считать тайм-аут управления доказательством отказа VPN.
2. Проверить обновлённую подписку и передачу данных из v2rayTun через домашнюю
   и мобильную сеть. Сравнить с TCP-пробами того же времени.
3. Сохранить стабильный VDS основным. Дополнительную точку входа включать
   только после независимого тестирования; нестабильную облачную машину не возвращать.
4. Резервное имя само по себе не спасает при блокировке того же IP.
   DNS упрощает смену адреса, но обновление зависит от кэша и переподключения.
   IPv6 не даёт невидимости и без глобального IPv6/маршрута не включается.

Проверяемые параметры REALITY описаны в [официальной документации Xray](https://xtls.github.io/en/config/transports/reality.html).
Статус Xray читается через [API сервера 3X-UI](https://docs.sanaei.dev/docs/reference/api/server/).
